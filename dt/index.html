iOS standalone viewport test matrix

Nine one-file probes. Each isolates one head/manifest variable. No network, no data, no login.

How to run each one (2 minutes each):
  1. Tap the variant below — it opens in Safari.
  2. Share sheet (square with arrow) → Add to Home Screen → Add.
  3. Go to the Home Screen and open the new icon (not the Safari tab — the tab always says FAIL).
  4. Screenshot it (side button + volume up).
  5. Delete the icon again. Move to the next variant.
If you already have an old icon for a variant, delete it first — iOS caches the manifest per installed app.

What to look for in the screenshot

  • Every page has a red bar pinned to the very top of the web view and a blue bar pinned to the very bottom.
  • PASS = red bar touches the top of the physical screen (under the Dynamic Island) and blue bar touches the bottom edge, with no foreign colour beyond either.
  • Any strip of colour above the red bar or below the blue bar is the unpainted band. Its colour names the culprit:
    • #FF00FF magenta → painted from the manifest theme_color
    • #00FF00 lime → painted from the manifest background_color
    • #0000FF blue-violet or #FFFF00 yellow → painted from the theme-color meta (and it does follow prefers-color-scheme — blue in Light, yellow in Dark)
    • white / black → painted from neither; iOS default
  • The big number line reads innerHeight / screen.height. Also note 100lvh in the table — if 100lvh is bigger than 100dvh, the paint-over fallback is available.

Tier A — run these four first

If any of these PASSes, stop: that is the fix.

At1
CONTROL — the app's exact current config
manifest linked · display:standalone · black-translucent · viewport-fit=cover · theme-color metas
Expected: reproduces the bug. This is the calibration shot.
 At7
LEGACY PURE — no manifest, no theme-color meta
apple-mobile-web-app-capable + black-translucent + viewport-fit=cover, nothing else
Highest chance of PASS. Removes both suspects at once.
 At2
NO MANIFEST (theme-color meta kept)
Isolates <link rel="manifest"> as the trigger. t7 PASS + t2 FAIL ⇒ the theme-color meta is the culprit. t7 PASS + t2 PASS ⇒ the manifest is.
 At4
NO COLOURS ANYWHERE (manifest kept)
manifest with no theme_color and no background_color, and no theme-color meta
If the band disappears or turns black, the colour declaration is what makes iOS reserve the bar.

Tier B — only if all of Tier A fails

Bt3
manifest display:fullscreen + display_override
Tests whether fullscreen escapes the reserved status-bar band.
 Bt5
black-translucent, no viewport-fit=cover
Tests whether cover is being applied at all. If t5 and t1 measure identically, cover is a no-op here.
 Bt6
MANIFEST ONLY — no apple-mobile-web-app-capable, no status-bar-style
The modern spec-only config. Also confirms whether the manifest alone still produces display-mode: standalone.
 Bt8
CALIBRATION — status-bar-style: default, deliberately opaque
Expected FAIL by design. Compare its band against t1's: if they look identical, iOS is treating black-translucent exactly as if it were default.

Tier C — run this one regardless

Ct9
FALLBACK FIX — control config + a height:100lvh full-bleed painter
A fixed, z-index:-1 layer sized 100lvh with a cyan 120px foot.
If the cyan bleeds past the blue bottom bar and fills the band, the app can paint over the strip itself — that is the guaranteed fix even if the viewport stays at 894.

What to send back

The 5 screenshots (t1, t7, t2, t4, t9) — or just the ones where the verdict line or the band colour changed versus t1. The full numeric table in each shot is what matters most.
